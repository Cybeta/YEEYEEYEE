# 规格：设定图锁定与参考图

> 状态：**五步都做完了。**第 5 步的结论是「视频接口只收一张，所以改为如实说明」；
> 第 2 步的图生图那条路是**刻意不做**（底图已占住参考位），不是漏做。
> **多参考图已经在真机上跑通一次**（三张设定卡 → 四槽工作流 → 出片），见「实测：真机跑通那一次」。
> 基线 2026-10-04。

## 要解决什么

第一集主角手里是剑，第二集变成刀——**文字描述锁不住一件东西的具体形制**。角色、道具、场景都是这样：它们会跨镜、跨集复现，只要有一处靠模型现编，就会出现「同一个人越拍越不像」「同一件道具换了样子」。

这条链在项目里是**已经定好的**——`GenerationStage` 的枚举顺序就是依赖顺序：

```
设定图（角色 / 场景 / 道具）→ 分镜图 → 分镜视频 → 成品视频
```

它自己的注释里写清了理由：分镜图在设定图之前也能出一张，但那张脸是模型现编的、跟第一张对不上；到出视频时更是一镜换一个人。本规格要补的是两件事——**把设定图真的当参考图喂进去**，以及**锁住之后还要能发现它被改了**。

## 现状：已有什么 / 缺什么

已有的：

- 三层数据结构都在：实体 → 变体 → 变体附件。**道具图与角色图存在同一个地方**（`WorkflowEntityVariant.Attachments`），不需要新模型。
- 引用是稳定的：分镜节点按「实体 + 变体」指向设定，画布记录着这件事。
- **引用过期**已经实现：一份设定改了图，所有引用它的分镜会被标出来。
- **技能那条路已经会送参考图**：按节点引用顺序取各实体附件里的图片，且支持 `ref:N` 下标。
- 池子的参考图能力是**探测出来的**（`SupportsReference` / `MaxReferenceImages`）。

缺的（就是本规格要做的四件）：

1. **节点右键那套出图不吃引用实体的图。** 它今天的参考图只有一个来源：`decision.BaseImageReference`——上一次尝试的那张，或你手挑的那张。
2. **张数上限默认 1**（`ImageMaxReferenceImages`）。而「角色 + 道具 + 场景」起步就要 3 张。
3. **寻址不稳。** `ref:N` 的下标是按「引用顺序把所有引用的所有图片拍平」得出的；角色带三视图（3 张）时，道具与场景的下标会被整体推后——道具排第几，取决于角色带了几张图。
4. **ComfyUI 侧只自动绑一处 `LoadImage`**（绑定器取第一个）。有多处参考图槽的工作流，其余槽位还留着导出时的占位文件名，会跑错或跑挂。

## 规则一：谁该被锁

判据是**会不会复现**，不是实体类别。

| | 例子 | 做法 |
|---|---|---|
| 会跨镜 / 跨集复现 | 主角、配角、主角的剑、信物、车、制服、常驻场景 | **必须锁**：有自己的设定图，被引用时进参考图 |
| 只在一镜出现 | 桌上那半张相纸、雨里的路牌、一次性路人 | 写提示词即可 |

这条要落到界面上：用户建了一件道具却没给它出设定图时，程序应当**说出来**——「这件道具被 3 个分镜引用，但还没有设定图，它每一镜都可能是另一个样子」，而不是默默放过。

## 规则二：张数与寻址

本规格里最容易做错的一件，先定规则再动手。

1. **参考图按槽位寻址，不按位置拍平。** 槽位 = `引用序号 + 变体 + 该变体的第几张图`。`ref:N` 这种下标只留给技能作者的提示词，**不作为内部寻址**——它对「某个变体带了几张图」太敏感。
2. **一镜的参考图上限**取三者最小值：用户设置（`ImageMaxReferenceImages`）、所选池子探测到的能力（`MaxReferenceImages`）、所选工作流模板能吃的参考图槽数（走 ComfyUI 时）。
3. **顺序固定为「角色 → 道具 → 场景」，同类内按引用顺序。** 顺序要稳定，因为它影响出图结果；界面上要把「这一镜实际会喂哪几张、按什么顺序」列出来给人看。
4. **超上限时的降级必须是显式的、可预期的**，不能悄悄丢：
   - 先按**复现次数**排（被引用得多的优先），再按类别（角色 > 道具 > 场景）；
   - 被丢掉的要在**动手前**说出来：「这一镜引用了 4 张参考图，这个池子最多吃 2 张，会丢掉『茶壶』『门牌』」；
   - 用户能手动指定这一次用哪几张，覆盖默认顺序。
5. **变体带多张图时**（例如角色三视图）：默认只取**第一张**作为该实体的参考图，其余留给用户显式选择——否则一个「角色三视图」会一口吃掉三个槽位。

## 规则三：锁有两半，两半都要

- **喂图**：出图与出视频两条路都要把引用实体的图当参考图送出去（今天只有技能那条路送了）。
- **变化提醒**：设定改了图，引用它的分镜要被标出来。**这一半已经有了**，本规格只需把它接到新路径上。

少了第二半，锁住的图哪天被替换，引用它的分镜不会提醒——锁就成了哑锁。

## 落地步骤与验收

按这个顺序做，每一步都能单独验：

1. **给「缺设定图的被引用实体」出提示**（只读，不改数据）——**已做**，并顺带修了两处真问题：
   - **已做**：这一层本来就有（`GenerationAudit.SettingImageLayer` 的第一条 + `GalleryOnlyNeeds`），
     所以没有从零写，而是把它真正的漏洞补上、并把规则钉住。
   - **修正一（引用落点）**：参考图取自**变体**，而设定节点出图的产物挂在**节点**上。
     节点有图、变体没图的中间态原来判「齐了」——可引用它的分镜一张参考图都拿不到，
     这正是「第一集是剑、第二集变刀」的成因。现在单独报一条，并说清是**还没提交到引用**。
   - **修正二（设定节点的锚）**：自检靠节点自己的 `References` 认出「承载它的节点」。
     `UnifiedWorkTree.Project` 会写这条引用，但 `create_entity` 与 `create_node` 是分开的两步——
     模型没点名实体时就是一张没锚的设定卡，被判成「只能到引用画廊补图」且不可动作、进不了预勾。
     现在 `create_node` 会在没点名时按「同一种类、名字唯一相同」兜底锚上；同名有歧义就不猜。
   - 验收：一件被分镜引用、却没有附件的设定，在自检里被列为缺口；补上（**变体**上的）附件后消失。
     存量画布未迁移（按约定先不管），要补的是给它们建出场条目或在界面上手工锚一次。
2. **出图路径接参考图**——**已做**（先只接池子那条路，一张）。规则抽到共享层的
   `ReferenceImagePicker`：顺序固定 角色 → 道具 → 场景（同类内按引用顺序）、变体带多张图只取
   第一张、上限由调用方算好传进来（不碰配置，免得一个上限两处真值来源）。
   **超上限要说出丢了谁**、**上限 0 要如实说没喂**——悄悄丢图等于悄悄降一致性。
   已接进桌面端的出图装配：文生图时带上（图生图不带——底图已占住参考位，混进去会改变它的语义），
   状态栏同时写出「带了哪几张 / 丢了哪几张」；池子声明不支持参考图时如实说没带。
   **上限已按规则二取小**（补做）：`ReferenceCapResolver` 把**用户设置、池子清单里声明的张数、
   这份工作流的底图入口数**三处取小，并记下**是卡在谁身上**，状态栏据此措辞——不然明明是
   「这家池子只吃 1 张」，却说成「你去改设置」，把人指去改错的地方。两处细节是刻意的：
   **0 与「没声明」分开**（设置填 0 是「不带参考图」，是真实约束；池子没写张数是「不知道」，
   不该反过来把用户的上限压成 0）；**工作流没有底图入口按 0 算**（塞进去只会白跑一次）。
   **未做**：图生图那条路——底图已占住参考位，把设定图混进去会改变它的语义，这是刻意的取舍，不是漏做。
3. **槽位寻址与顺序**（含降级，以及「实际会喂哪几张」的展示）——**已做**：
   顺序固定、降级要列出来、变体只取第一张，三条都被用例钉住了。
   「角色带 3 张图时道具的下标不被推后」这条由**「变体只取第一张」**保证——一个实体只占一个位置，
   它带几张图不影响后面。
   **「手动指定这一次用哪几张」已做**（原先只剩这一半，要界面）：出图对话框里多一块
   「参考图（这一镜会喂哪几张）」，候选按默认顺序列出来、默认全勾，取消勾选就只喂勾上的那几张；
   下面那行**实时**写着「带哪几张 / 丢哪几张 / 卡在谁身上」——点下去之前就看得见，而不是等状态栏事后补一句。
   两条实现上的规矩：按**实体 + 变体**点名（不按下标——下标会随「引用的先后」「某个变体带了几张图」变，
   点错了不会有任何报错）；**先筛再裁**（反过来的话，被排除的那张会白占一个上限名额，本该留下的反而被丢掉）。
   上限那一份只算在**一处**（`ResolveReferenceCap`），对话框与装配共用——两处各算一遍迟早会对不上，
   而那句话正是点下去之前唯一的依据。
   「这一次不勾」**不改画布上的引用**：这一镜先不要它，和以后都不要它，是两件事。
4. **ComfyUI 多参考图槽的自动绑值**——**已做**。`ImageNodeIds` 收全部底图入口（按节点 id 稳定排序），
   `ImageNames` 按顺序对号入座；给不满时只写前几个入口、**多出来的保持它原来的示例图**
   （不拿同一张图去凑数：那样等于谎报输入）。`ImageNodeId` 仍是第 1 个，所以单图那条路一字未动，
   四份真机样本的逐字对拍照旧通过。
   **合集型要按组填**（补做）：`ImageGroups` 把入口按「能通到哪个输出节点」分组，多组时
   **每组各取前 k 张**，而不是平铺到前几个入口——平铺的话图会全落进前两个小组，真正能收多张的
   那组一张都拿不到（实测 `B03`）。分不清（有入口走不到任何输出）时退回一次到位的平铺。
   `ImageCapacity` = 最大一组的槽数，**不是入口总数**——合集型的入口总数是各组之和（`B03` 是 6），
   拿它当上限会算出一个虚高的额度。分组规则与实测见下一节。
5. **视频路径接上**（首帧之外的参考图）——**已做，但结论是「接口吃不下，所以要说出来」**。
   `RunVideoAsync` 现在把首帧排在第一位、引用的设定图跟在后（顺序不能颠倒：`ReferenceImages[0]`
   就是图生视频的起点，换了就等于换了这一镜的起点）；`IVideoProvider` 新增 `ReferenceCapacity`
   （与出图侧对称），`HttpVideoProvider` 报 **1**——我们这个视频接口的提交体只有一个 `image` 字段；
   多出来的由它在 `VideoGenerationResult.ReferenceNote` 里说明，状态栏写在最前面。
   **实际能带的仍然只有一张**：这一步的价值是把它**说清楚**，而不是假装带上了——不说的话，
   用户会以为设定生效了，然后一直找模型的问题。真要带多图得等接口支持，那时只改
   `ReferenceCapacity` 一处，调用方不必动。

## 实测：这批工作流里有多少份真能吃多张参考图

用产品自己的 `ComfyUiWorkflowBinder.Detect`，在**重转后**的 315 份正文上逐份跑（不是估的，随时可复算）：

| 项 | 份数 | 说明 |
|---|---|---|
| 有底图入口（`LoadImage` 且 `image` 是字面量） | **210** | 单图那条路能用的 |
| 有 **2 个及以上**底图入口 | **73** | 第 4 步放开后能收多张的 |
| 其中**只有一组** | **67** | 平铺就是对的 |
| 其中**多组** | **6** | 改动前会填错组；现在走按组填 |
| 入口**全都悬空**（没有任何下游） | **9** | 修 bug 前是 10——有一条原本断掉的入口被接了回来 |

那 6 份是 `B01编辑Qwen编辑合集`、`B03编辑Qwen2511单双三图编辑V2`、`B04编辑Qwen2511多角度多场景分镜`、
`D17Klein9B全自动换脸任意姿势编辑`、`G16合集图生视频大合集`、`G21图生视频大丝袜81单双三图`——
名字里明写着「合集」「单双三图」，与「几组各自带一个输出」这个形状对得上，算是分组算对了的旁证。

还有一处必须说清：**这几个数与旧表（205 / 72 / 31）对不上，是口径不同，不是修 bug 改的。**
拿同一个工具跑重转前后的两份正文，入口数前后都是 210 / 73——旁路 bug 丢掉的是**进去的线**，
不是入口本身；旧表那三个数是修 bug 前手工数 316 份（比现在多一份）得到的。

### 怎么分组，以及为什么按组填

**组 = 能通到同一个输出（保存类）节点的那些入口**，并查集聚类。只要有一个入口走不到任何保存节点，
就**不分组、退回一次到位的平铺**——分不清就不硬分（那 9 份入口全悬空的就落在这里）。

为什么必须分：合集型的工作流是**几条各自独立的管线并排放在一个文件里**。`B03编辑Qwen2511单双三图编辑V2`
就是「单双三图」三档并排、各走自己的 `SaveImage`：

- 节点 `220` 只收 `image1`（入口 `219`）——单图组，走 `SaveImage(216)`；
- 节点 `247`、`249` 各收 `image1/2`（`261`、`262`）——两图组，走 `SaveImage(243)`；
- 节点 `280`、`279` 各收 `image1/2/3`（`289`、`292`、`297`）——三图组，走 `SaveImage(277)`。

对它，「按节点 id 顺序平铺前 N 个入口」会把 3 张参考图全塞进单图组与两图组的第一槽，
**真正能收三张的那个三图组一张都拿不到**，仍留着导出时的示例图；界面报"成功"，出来的却不是你要的。
按组填则是**每组各取「角色 → 道具 → 场景」的前 k 张**（k = 这组有几个并列槽），组与组互不干扰：
前面那组少拿几张，最后一组拿满。

（原先这里猜的是「哪一组生效由工作流自己的开关决定」。逐节点核过 `B03` 与 `F01` 之后发现不成立：
`B03` 里**一个开关都没有**；`F01` 里那三个 `Switch any [Crystools]` 在**下游选结果**，
`boolean` 来自另一个节点，跟「用哪张图」无关。所以走的是「按输出分组」这条，不认开关。）

反面参照——**单组**的形状长这样：
`U01minimaxh3多图参考生视频基础版` 的 `MiniMaxH3ReferenceToVideo` 有一个 `ref_images` 对象输入，
里面是 `ref_image_0..ref_image_3`，由 137、139、141、161 依次接上；给 3 张就落进前三个，
第四个保持原样。**挑工作流时要认这个形状**，而不是只数 `LoadImage` 的个数。

服务端恢复后按原计划跑了一遍：三张设定卡（角色正面半身、道具红罩台灯、场景老城照相馆内景）走
`U01minimaxh3多图参考生视频基础版`——一份 `ref_images.ref_image_0..3` 的单组工作流，喂前三个槽。

- 产出 `comfyui_00004_.mp4`（1.18 MB，244 帧 @24fps ≈ 10.2 秒）。落地后看了首帧、中帧、尾帧：
  红汉服少女、白狐、船篷与油灯、莲叶与夜雾都在，人物与道具跨帧一致，白狐按提示词从警觉转成伏卧。

**第一次跑是不出片的**——那不是这个规格的问题，是转换器的一个 bug，见下。

## 顺带修掉的转换器 bug：被绕过的节点只删不接线

第一次提交时服务端回 `success`、耗时 370 秒，**产出为空**。查下来：

- 这份工作流的 `CreateVideo(130).images` 是必填项，可转出来的 API 里**没有这一项**；
- 它的源头是 `RTXVideoSuperResolution(157)`，在网页格式里是 `mode=4`（被绕过，编辑器里的 Ctrl+B）；
- 老转换器把 `mode=4` 的节点**直接删掉**、却没接它本该转发的线——`VAEDecode(122)` 解出来的帧
  就这么断了，`CreateVideo` 拿不到画面，`SaveVideo` 自然一个文件都不落。

规则本来就在官方前端里（`src/utils/executionUtil.ts` 的 `ExecutableNodeDTO.resolveOutput()`）：
被绕过的节点按**类型**挑一个顶得上的输入槽，再顺着它的连线往上走；静音（`mode=2`）才是真的不产出。
我们之前只把这条规则用在 `Reroute` 上（那次修的是 `required_input_missing`），漏了旁路这一支。

修完在真文件上复核：`CreateVideo.images` 回到 `["122",0]`，重跑那次就出了片。

**影响面先估了一次，再用真重转校准。** 第一步是把站点上 315 份原始工作流全下来扫一遍：
被绕过的后端节点 2021 个，其中「夹在两个都活着的节点中间」的 186 个、涉及 80 份。
但那个 186 是**上界**——它只看「两头有没有连线」，没看旁路时到底能不能按类型找到顶得上的输入槽。

于是用新转换器把这 315 份**真重转了一遍**，拿新旧正文逐项对账，这才是准数：

| 项 | 数量 |
|---|---|
| 补回连线的文件 | **62 / 315** |
| 补回连线 | **127 条** |

重转这次：315 份全部转换成功、**0 失败**；正文有变化的正好也是这 62 份，而且变化**全是新增项**——
没有一份是因为别的原因变的。（这也说明那个 186 里有一多半其实穿不过去：上游自己也被绕过、
或者按类型找不到对应的输入槽，那两种情形官方前端同样会丢掉这个输入。）

像 `T04` 那样**整条链一起被绕过**的不算：它下游本来就不进 API，少不少那一项没差别。
这也解释了四份逐字对拍样本为什么一直没抓到这个 bug：样本里唯一带旁路的 `T04`，
恰好就是整条链一起绕过。

## 还没验到的

- **第 3 步的界面我没有眼睛看。** 勾选那一块的行为（候选顺序、先筛再裁、说明措辞、一张不勾的说法）
  都有用例钉住，但**长相与手感要人来试**——按约定 UI 由使用者手测，这里不做点击测试。
  手测时值得看的几点：候选顺序是不是 角色 → 道具 → 场景；换接口后下面那行有没有跟着重算；
  取消勾选后那行有没有立刻变；「这一次不勾」之后画布上的引用有没有被动过（**不该被动**）。
- 视频那条路**能不能带多图，取决于接口**。我们现在能确认的只有「我们这家接口只收一张」
  （提交体一个 `image` 字段）；别家若支持多图，得先把它的能力探测出来——`SitePoolProbe` 已经会读
  `max_reference_images`，但**视频站没按站点导入时那份能力拿不到**（只有地址 + 模型名）。
  所以视频侧现在恒为 1，是「按已知事实保守」，不是「探测过」。要做得更准，得先把视频站导入成站点。
- 合集型现在是按组填了，但**组的语义仍然是我们定的**：每组各取「角色 → 道具 → 场景」的前 k 张，
  靠的是我们那条固定顺序。若某份工作流的三条管线语义不同（例如一条要「衣服」、一条要「人」），
  我们无从知道，只能按顺序给——这跟「不替使用者决定」是一致的，但得说清楚。
- 上面那次真机跑的是**「多参考图」这一类**（工作流自己的 `ref_images` 入口），
  **不是**分镜节点右键那条出视频的路——那条路的 ComfyUI 提交还没接上。

## 已知限制 / 不打算做的

- **锁的是「形制」，不是像素级一致。** 参考图能显著提高跨镜一致性，但不会让第二集那把剑与第一集逐像素相同。真要逐像素一致，靠的是剪辑复用素材，不是再生成一次。
- **参考图不是越多越好。** 多张低质量参考图会互相打架；界面上不鼓励「全都塞进去」。
- **不做「自动替用户决定用哪几张」的默认魔法。** 默认顺序固定、可预期，超限降级必须说出来——这与项目既有的「不替使用者决定」一致。
