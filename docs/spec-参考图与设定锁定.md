# 规格：设定图锁定与参考图

> 状态：**第 1、2、4 步已做；第 3 步的规则部分已做**（「手动指定这一次用哪几张」要界面，未做）；第 5 步未实现。
> 底线：**没有真机跑过一次多参考图生成**——写这份更新时服务端不可用，见「没验到的」。
> 基线 2026-10-04。

## 要解决什么

第一集主角手里是剑，第二集变成刀——**文字描述锁不住一件东西的具体形制**。角色、道具、场景都是这样：它们会跨镜、跨集复现，只要有一处靠模型现编，就会出现「同一个人越拍越不像」「同一件道具换了样子」。

这条链在项目里是**已经定好的**——`GenerationStage` 的枚举顺序就是依赖顺序：

```
设定图（角色 / 场景 / 道具）→ 分镜图 → 分镜视频 → 成品视频
```

它自己的注释里写清了理由：分镜图在设定图之前也能出一张，但那张脸是模型现编的、跟第一张对不上；到出视频时更是一镜换一个人。本规格要补的是两件事——**把设定图真的当参考图喂进去**，以及**锁住之后还要能发现它被改了**。

## 现状：已有什么 / 缺什么

已有的：

- 三层数据结构都在：实体 → 变体 → 变体附件。**道具图与角色图存在同一个地方**（`WorkflowEntityVariant.Attachments`），不需要新模型。
- 引用是稳定的：分镜节点按「实体 + 变体」指向设定，画布记录着这件事。
- **引用过期**已经实现：一份设定改了图，所有引用它的分镜会被标出来。
- **技能那条路已经会送参考图**：按节点引用顺序取各实体附件里的图片，且支持 `ref:N` 下标。
- 池子的参考图能力是**探测出来的**（`SupportsReference` / `MaxReferenceImages`）。

缺的（就是本规格要做的四件）：

1. **节点右键那套出图不吃引用实体的图。** 它今天的参考图只有一个来源：`decision.BaseImageReference`——上一次尝试的那张，或你手挑的那张。
2. **张数上限默认 1**（`ImageMaxReferenceImages`）。而「角色 + 道具 + 场景」起步就要 3 张。
3. **寻址不稳。** `ref:N` 的下标是按「引用顺序把所有引用的所有图片拍平」得出的；角色带三视图（3 张）时，道具与场景的下标会被整体推后——道具排第几，取决于角色带了几张图。
4. **ComfyUI 侧只自动绑一处 `LoadImage`**（绑定器取第一个）。有多处参考图槽的工作流，其余槽位还留着导出时的占位文件名，会跑错或跑挂。

## 规则一：谁该被锁

判据是**会不会复现**，不是实体类别。

| | 例子 | 做法 |
|---|---|---|
| 会跨镜 / 跨集复现 | 主角、配角、主角的剑、信物、车、制服、常驻场景 | **必须锁**：有自己的设定图，被引用时进参考图 |
| 只在一镜出现 | 桌上那半张相纸、雨里的路牌、一次性路人 | 写提示词即可 |

这条要落到界面上：用户建了一件道具却没给它出设定图时，程序应当**说出来**——「这件道具被 3 个分镜引用，但还没有设定图，它每一镜都可能是另一个样子」，而不是默默放过。

## 规则二：张数与寻址

本规格里最容易做错的一件，先定规则再动手。

1. **参考图按槽位寻址，不按位置拍平。** 槽位 = `引用序号 + 变体 + 该变体的第几张图`。`ref:N` 这种下标只留给技能作者的提示词，**不作为内部寻址**——它对「某个变体带了几张图」太敏感。
2. **一镜的参考图上限**取三者最小值：用户设置（`ImageMaxReferenceImages`）、所选池子探测到的能力（`MaxReferenceImages`）、所选工作流模板能吃的参考图槽数（走 ComfyUI 时）。
3. **顺序固定为「角色 → 道具 → 场景」，同类内按引用顺序。** 顺序要稳定，因为它影响出图结果；界面上要把「这一镜实际会喂哪几张、按什么顺序」列出来给人看。
4. **超上限时的降级必须是显式的、可预期的**，不能悄悄丢：
   - 先按**复现次数**排（被引用得多的优先），再按类别（角色 > 道具 > 场景）；
   - 被丢掉的要在**动手前**说出来：「这一镜引用了 4 张参考图，这个池子最多吃 2 张，会丢掉『茶壶』『门牌』」；
   - 用户能手动指定这一次用哪几张，覆盖默认顺序。
5. **变体带多张图时**（例如角色三视图）：默认只取**第一张**作为该实体的参考图，其余留给用户显式选择——否则一个「角色三视图」会一口吃掉三个槽位。

## 规则三：锁有两半，两半都要

- **喂图**：出图与出视频两条路都要把引用实体的图当参考图送出去（今天只有技能那条路送了）。
- **变化提醒**：设定改了图，引用它的分镜要被标出来。**这一半已经有了**，本规格只需把它接到新路径上。

少了第二半，锁住的图哪天被替换，引用它的分镜不会提醒——锁就成了哑锁。

## 落地步骤与验收

按这个顺序做，每一步都能单独验：

1. **给「缺设定图的被引用实体」出提示**（只读，不改数据）——**已做**，并顺带修了两处真问题：
   - **已做**：这一层本来就有（`GenerationAudit.SettingImageLayer` 的第一条 + `GalleryOnlyNeeds`），
     所以没有从零写，而是把它真正的漏洞补上、并把规则钉住。
   - **修正一（引用落点）**：参考图取自**变体**，而设定节点出图的产物挂在**节点**上。
     节点有图、变体没图的中间态原来判「齐了」——可引用它的分镜一张参考图都拿不到，
     这正是「第一集是剑、第二集变刀」的成因。现在单独报一条，并说清是**还没提交到引用**。
   - **修正二（设定节点的锚）**：自检靠节点自己的 `References` 认出「承载它的节点」。
     `UnifiedWorkTree.Project` 会写这条引用，但 `create_entity` 与 `create_node` 是分开的两步——
     模型没点名实体时就是一张没锚的设定卡，被判成「只能到引用画廊补图」且不可动作、进不了预勾。
     现在 `create_node` 会在没点名时按「同一种类、名字唯一相同」兜底锚上；同名有歧义就不猜。
   - 验收：一件被分镜引用、却没有附件的设定，在自检里被列为缺口；补上（**变体**上的）附件后消失。
     存量画布未迁移（按约定先不管），要补的是给它们建出场条目或在界面上手工锚一次。
2. **出图路径接参考图**——**已做**（先只接池子那条路，一张）。规则抽到共享层的
   `ReferenceImagePicker`：顺序固定 角色 → 道具 → 场景（同类内按引用顺序）、变体带多张图只取
   第一张、上限由调用方算好传进来（不碰配置，免得一个上限两处真值来源）。
   **超上限要说出丢了谁**、**上限 0 要如实说没喂**——悄悄丢图等于悄悄降一致性。
   已接进桌面端的出图装配：文生图时带上（图生图不带——底图已占住参考位，混进去会改变它的语义），
   状态栏同时写出「带了哪几张 / 丢了哪几张」；池子声明不支持参考图时如实说没带。
   **未做**：图生图那条路；上限只按设置里那张算，没取池子探测到的那份。
3. **槽位寻址与顺序**（含降级，以及「实际会喂哪几张」的展示）——**规则部分已做**：
   顺序固定、降级要列出来、变体只取第一张，三条都被用例钉住了。
   「角色带 3 张图时道具的下标不被推后」这条由**「变体只取第一张」**保证——一个实体只占一个位置，
   它带几张图不影响后面。
   **未做**：「手动指定这一次用哪几张（覆盖默认顺序）」——这条要界面，没有它用户只能用
   「取消引用」来表达"这一镜不要它"。
4. **ComfyUI 多参考图槽的自动绑值**——**已做**。`ImageNodeIds` 收全部底图入口（按节点 id 稳定排序），
   `ImageNames` 按顺序对号入座；给不满时只写前几个入口、**多出来的保持它原来的示例图**
   （不拿同一张图去凑数：那样等于谎报输入）。`ImageNodeId` 仍是第 1 个，所以单图那条路一字未动，
   四份真机样本的逐字对拍照旧通过。
   **注意它的适用范围**：见下节最后一行——绑值按顺序填前 N 个入口，只在「多个入口是同一个节点的
   并列输入」时才等于"多参考图"。
5. **视频路径接上**（首帧之外的参考图）——未做。

## 实测：这批工作流里有多少份真能吃多张参考图

逐份读了导入的 316 份 payload（不是估的）：

| 项 | 份数 | 说明 |
|---|---|---|
| 有底图入口（`LoadImage` 且带 `image`） | **205** | 单图那条路能用的 |
| 有 **2 个及以上**底图入口 | **72** | 第 4 步放开后能收多张的 |
| 多张底图**通向同一个节点** | **31** | 真正的多参考图合成；其余是「多入口但分属不同分支」 |

最后一行是这一节最要紧的：**绑值按顺序填前 N 个入口**，只在「多个入口是同一个节点的并列输入」时
才等于"多参考图"。入口分属不同分支时（例如各自接到一个 `…Switch`），填它们只是换掉几条备选支路的图，
**用哪条仍由开关决定**——那种工作流要真用上多图，得先认得出开关的选择。那是另一件事，本规格没做。

## 没验到的（外部阻塞）

写这份更新时，`ComfyUiBaseUrl` 指向的那台 ComfyUI 已经不响应了：nginx 对 `/`、`/prompt`、
`/api/prompt`、`/history`、`/api/system_stats` **一律 404**（实例重启，或隧道换了目标）。所以：

- 上面那张表是**读文件数出来的**，可信；
- 「三张图真的按顺序到了服务端、并被三个入口分别收到」**没有真机验过**。绑定这一侧有单元证明
  （`Bind` 返回的就是会被 POST 到 `/prompt` 的那份 JSON，用例逐字核过「给两张」与「只给一张」两种），
  但从界面点下去到服务端收到那一段，缺一台能跑的服务端；
- 服务端恢复后要跑的东西已经定好：候选是上面 31 份里 `MinimaxH3` 的多图参考类（语义最对）；
  素材是三张设定卡（角色正面半身、道具红罩台灯、场景老城照相馆内景）。

## 已知限制 / 不打算做的

- **锁的是「形制」，不是像素级一致。** 参考图能显著提高跨镜一致性，但不会让第二集那把剑与第一集逐像素相同。真要逐像素一致，靠的是剪辑复用素材，不是再生成一次。
- **参考图不是越多越好。** 多张低质量参考图会互相打架；界面上不鼓励「全都塞进去」。
- **不做「自动替用户决定用哪几张」的默认魔法。** 默认顺序固定、可预期，超限降级必须说出来——这与项目既有的「不替使用者决定」一致。
